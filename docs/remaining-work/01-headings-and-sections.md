# 工程1：本文の見出し・章構造

## 目的と開始条件

PDFの明示情報・座標と本文sourceの対応を根拠に、見出しと節の関係をモデルへ追加し、EPUBの本文要素と目次に反映します。Stage 12aのしおり250件はページへのリンクとしてすでに動きますが、本文見出し・章境界は未実装です。

[共通手順](README.md) を済ませ、[Stage 12b調査](../stage12b-structure-evidence.md) と [Stage 12a仕様](../stage12a-outline-navigation.md) を読みます。現在のコーパスに明示タグがなかったという結果を再調査だけで置き換えず、対応付けの根拠へ進みます。

## 1A：対応付けの根拠を調べる

1. 開始SHAと入力指紋を固定し、全250しおりについて、匿名PDF ID、outline path、元destination、named destinationの解決値、対象ページ、座標指定の種類をローカルに記録します。named destinationの名前だけを座標証拠とみなしません。
2. 対象ページのsource ranges、物理行／列、glyph geometryを既存のinspectionから取得します。PDF座標とdisplay座標を混ぜず、viewport変換・回転・UserUnitを記録します。
3. ページ全体を示すdestination、位置の一部がnullのdestination、同じページに複数の項目、親子の同一参照、非単調な順序、重複／ページ範囲外の参照を分類します。タイトルの部分一致だけで本文位置を選びません。
4. 対応候補を `一意に根拠がある / 複数候補 / ページまでしか分からない / 対応不能` に分けます。各分類について全件数と理由別件数を出し、合計が250であることを確認します。ここでの分類名は設計用で、既存APIではありません。
5. 同一座標に別の文字列、同じタイトルが複数箇所にある場合、縦書きと0/90/180/270度回転、リガチャと補助文字を含む実PDF fixtureを作ります。候補の選択が文字の見た目やPDFの出所に依存しないことを確認します。
6. 「見出しの開始／終端を確定できる条件」と「リンク先だけ分かる条件」を別々に文書化します。座標で近いだけなら後者です。調査結果をレビューしてから1Bへ進みます。

成果物：匿名集計、局所的な反例、座標／source対応の契約、未解決理由。本文や私的サンプル名はGitに載せません。根拠が確立しなければ1Aのチェックポイントとして保存し、機能全体は保留とします。

## 1B：モデルと検証を実装する

1. source storeと元のしおりを変更せず、見出しのsource ranges、レベルの根拠、節との関係、outline path、解決状態を持つ型を設計します。HTMLやCSSをモデルへ保存しません。
2. 見出しレベルをoutlineの深さと同一とする場合は、その意味上の根拠を示します。単に木が深いことをH2/H3の確定根拠にしません。確定できないレベルは未確定として扱います。
3. 節は本文を複製するコンテナではなく、既存ブロック／範囲への関係として扱う設計を優先します。前付け・後付け、ページ内での節境界、ページをまたぐ節、最後の節の終端を定義します。次のしおりまでを自動的に一章とみなしません。
4. ブロックの分割が必要な場合、既存inlineと正確なルビの所有を保存して分割します。リガチャやルビの内部に不確かな境界が来る場合は分割しません。
5. validatorへ、参照先の存在、範囲の重複／欠落、節の循環、順序、元タイトル／sourceとの不一致を検出する条件を追加します。原文を持たない見出しの捏造を拒否します。

## 1C：EPUBへ反映する

1. 確定した見出しだけを適切な本文要素へ出力します。元のテキストを別途挿入して二重表示にしません。
2. source参照から決定的な本文idを割り当て、一意性と存在を検証します。目次の精密リンクは確定したidに限り、未確定の場合はStage 12aのページリンクを保持します。
3. まず既存の「source 1ページ＝XHTML 1ファイル」を保ったまま実装します。章ごとのファイル分割は必須にせず、必要なら別の設計差分としてspine・page-list・sourceページ数への影響を先に示します。
4. unresolvedしおりの表示方針と全ページへのアクセスを維持し、目次の有効リンクがすべて実在する本文へ到達するか実ZIPから検証します。

## 検証と完了条件

[共通の全検証](README.md) に加え、次を確認します。

- 実データの250項目すべてに新しい解決状態または既存fallbackがあり、分類漏れ0件。
- 採用する規則について、対応可能な実データのsource境界を確認し、全新規対応の構造検証と代表例の目視レビューを記録する。陽性fixtureだけの成功を実コーパスでの実証に置き換えない。
- 見出しなし、同名見出し、親子同一ページ、複数節／ページ、回転、縦書き、補助文字、空白、ルビをまたぐ候補のfixtureが期待どおり。
- 宣言した意味付け以外のsource文字列と所有が不変。5,141ページの保存、ルビ／注記保存、目次参照整合、EPUBCheck全9冊合格。
- モデル化、本文出力、リンク検証まで実装されている。調査ツールだけでは工程1を完了としない。

誤った見出し、本文欠落／二重化、既存exactルビの破損、根拠のない章境界を1件でも見つけたら、その規則の採用を止めます。根拠不足で対応範囲を縮小する場合は制限を提示し、必須の完成範囲を変更する判断だけをユーザーに確認します。通常の修正・検証・承認済みpushには再承認を挟みません。

最後に [レビュー書式](review-template.md) を埋め、共通の公開手順でpushします。次は工程2です。
